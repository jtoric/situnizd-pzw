\begin{frame}{Anatomija dobrog testa: Arrange - Act - Assert}
Svaki test ima tri dijela:

\vspace{0.4em}
\begin{tabular}{@{}lp{8.5cm}@{}}
  \toprule
  \textbf{Dio} & \textbf{Što radi} \\
  \midrule
  Arrange & Pripremi stanje: korisnik u bazi, token, natjecanje s rokom \\
  Act & Izvrši jednu akciju: pošalji request, pozovi funkciju \\
  Assert & Provjeri ishod: status kod, sadržaj odgovora, stanje u bazi \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
Ime testa opisuje pravilo, ne implementaciju: \texttt{test\_klub\_ne\_moze\_prijaviti\_nakon\_prelim\_roka} govori što je pravilo. Kad taj test padne, iz imena znate koje se pravilo prekršilo.

\vspace{0.4em}
Jedan test = jedno pravilo. Test koji provjerava pet stvari padne, a vi ne znate koja od pet je kriva.
\end{frame}

% ------------------------------------------------------------
\begin{frame}[fragile,shrink=5]{pytest fixtures: gradivni blokovi testova}
Fixture je funkcija koja priprema ono što test treba - pytest je poziva automatski po imenu parametra:

\begin{lstlisting}[language=python]
import pytest

@pytest.fixture
def competition_open():
    return Competition(
        name="Otvoreno prvenstvo",
        prelim_deadline=datetime(2027, 3, 1, tzinfo=timezone.utc),
        final_deadline=datetime(2027, 3, 15, tzinfo=timezone.utc),
    )

def test_faza_prije_prelim_roka(competition_open):
    with freeze_time("2027-02-01"):
        assert get_competition_phase(competition_open) == Phase.OPEN
\end{lstlisting}

\vspace{0.4em}
Fixture se definira jednom, koristi u koliko god testova treba. Kad se model promijeni, mijenjate jednu fixture umjesto dvadeset testova.
\end{frame}

% ------------------------------------------------------------
\begin{frame}[fragile,shrink=10]{conftest.py: dijeljene fixture za cijeli projekt}
\begin{lstlisting}[language=python]
# tests/conftest.py
import pytest
from httpx import AsyncClient, ASGITransport
from app.main import app
from app.core.deps import get_db

@pytest.fixture
async def client(db_session):
    # zamijeni pravu bazu test sessionom
    app.dependency_overrides[get_db] = lambda: db_session
    transport = ASGITransport(app=app)
    async with AsyncClient(
        transport=transport, base_url="http://test"
    ) as c:
        yield c
    app.dependency_overrides.clear()
\end{lstlisting}

\vspace{0.4em}
\texttt{conftest.py} je poseban file - fixture iz njega su dostupne svim testovima bez importa. \texttt{dependency\_overrides} je FastAPI mehanizam: sve što je \texttt{Depends(get\_db)} u testu dobiva našu test sesiju umjesto prave baze.
\end{frame}

% ------------------------------------------------------------
\begin{frame}[fragile,shrink=5]{Izolacija testova: transakcija + rollback}
\begin{lstlisting}[language=python]
@pytest.fixture
async def db_session():
    async with engine.connect() as conn:
        trans = await conn.begin()
        session = AsyncSession(bind=conn)
        yield session          # test radi u transakciji
        await session.close()
        await trans.rollback() # sve promjene nestaju
\end{lstlisting}

\vspace{0.4em}
Svaki test dobiva svježu transakciju koja se na kraju rollbacka. Posljedice:
\begin{itemize}
  \item testovi ne vide podatke jedni od drugih
  \item redoslijed izvršavanja ne mijenja rezultat
  \item nema \enquote{očisti bazu} koda na kraju svakog testa
\end{itemize}

\vspace{0.4em}
Test koji ovisi o podacima prethodnog testa je tempirana bomba - radi dok netko ne pokrene samo jedan test.
\end{frame}

\begin{frame}[fragile,shrink=5]{Fixture za tokene: testiranje kao admin i kao klub}
\begin{lstlisting}[language=python]
@pytest.fixture
async def admin_token(client):
    resp = await client.post("/auth/login", json={
        "username": "admin", "password": "admin123"})
    return resp.json()["access_token"]

@pytest.fixture
async def club_token(client):
    resp = await client.post("/auth/login", json={
        "username": "behemot", "password": "klub123"})
    return resp.json()["access_token"]

async def test_klub_ne_moze_kreirati_klub(client, club_token):
    resp = await client.post("/clubs",
        json={"name": "Novi klub"},
        headers={"Authorization": f"Bearer {club_token}"})
    assert resp.status_code == 403
\end{lstlisting}

\vspace{0.4em}
Za svaki endpoint pišemo barem jedan negativni test: pogrešna rola, tuđi resurs ili istekli rok.
\end{frame}

\begin{frame}[fragile,shrink=5]{freezegun: vremenska pravila (rekapitulacija P6)}
\begin{lstlisting}[language=python]
from freezegun import freeze_time

@freeze_time("2027-03-05")  # izmedu prelim i final roka
async def test_nova_prijava_nakon_prelim_roka(client, club_token):
    resp = await client.post(
        "/competitions/1/registrations",
        json={"lifter_id": 1, "category": "93"},
        headers={"Authorization": f"Bearer {club_token}"})
    assert resp.status_code == 400
    assert resp.json()["code"] == "deadline_passed"

@freeze_time("2027-03-05")
async def test_odjava_izmedu_rokova_prolazi(client, club_token):
    resp = await client.post(
        "/competitions/1/registrations/1/withdraw",
        headers={"Authorization": f"Bearer {club_token}"})
    assert resp.status_code == 200
\end{lstlisting}

\vspace{0.4em}
\texttt{freeze\_time} zamrzava \texttt{datetime.now()} na zadani trenutak. Bez toga bi testovi faza prolazili ili padali ovisno o stvarnom datumu pokretanja.
\end{frame}

\begin{frame}[fragile,shrink=5]{Coverage: koliko je koda pokriveno}
\begin{lstlisting}[language=bash]
uv pip install pytest-cov
pytest --cov=app --cov-report=term-missing

# Name                        Stmts   Miss  Cover   Missing
# app/services/registration.py  45      3    93%   88-90
# app/routers/clubs.py           30      0   100%
\end{lstlisting}

\vspace{0.4em}
\texttt{Missing} stupac pokazuje linije koje nijedan test ne izvršava - često su to error grane i edge caseovi, upravo ono što se najviše isplati testirati.

\vspace{0.6em}
Coverage mjeri \textbf{izvršenost}, ne ispravnost: linija može biti pokrivena testom koji ništa ne provjerava. 100\% coverage nije cilj - cilj je da su \textbf{poslovna pravila i error grane} pokriveni smislenim assertima. Za ovaj projekt: services i pravila blizu 100\%, boilerplate može niže.
\end{frame}

\begin{frame}[fragile,shrink=5]{E2E testovi: Playwright}
Playwright kontrolira pravi browser - testira što korisnik zapravo vidi i radi:

\vspace{0.4em}
\begin{itemize}
  \item Pokreće Chromium, Firefox ili WebKit
  \item Navigira, klikće, ispunjava forme - kao pravi korisnik
  \item Provjera: URL, tekst na stranici, vidljivost elemenata
  \item Automatski čeka da elementi budu dostupni (nema sleep/timeout)
\end{itemize}

\vspace{0.6em}
\begin{lstlisting}[language=bash]
npm install -D @playwright/test
npx playwright install   # preuzme browsere
\end{lstlisting}

\vspace{0.4em}
U komponentama dodajte \texttt{data-testid} atribute za stabilne selectore: \texttt{data-testid="username"} ne puca kad promijenite CSS klasu ili tekst labela.
\end{frame}

\begin{frame}[fragile,shrink=5]{E2E test: pravilo faze u UI-ju}

  ).toBeDisabled()
