\begin{frame}{Zahtjev 1: SPA s routingom}
\begin{itemize}
  \item \textbf{Najmanje 5 stranica}: login, lista glavnog entiteta, forma za unos ili uređivanje, detalji, admin pregled
  \item Vue Router s \codefile{createWebHistory} - navigacija bez refresha stranice
  \item Zajednički \textbf{layout}: navigacija s linkovima ovisnim o roli, logout gumb, prikaz prijavljenog korisnika
  \item Dinamičke rute s parametrima: \codefile{/lifters/:id/edit} ili ekvivalent u vašoj domeni
\end{itemize}

\vspace{0.4em}
Na obrani otvaram DevTools i klikćem po aplikaciji: ako se stranica refresha na svaku navigaciju, to nije SPA.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 2: auth flow}
\begin{itemize}
  \item \textbf{Login forma} koja poziva vaš \codefile{/auth/login} i sprema tokene
  \item Access token se šalje na svaki request kroz \textbf{Axios request interceptor}
  \item \textbf{Automatski refresh}: na 401 interceptor tiho zove \codefile{/auth/refresh} i ponavlja originalni request
  \item Kad refresh ne uspije: logout i redirect na login
  \item Auth stanje preživljava refresh stranice - \codefile{/auth/me} pri startu aplikacije
\end{itemize}

\vspace{0.4em}
Ovo testiram tako da ostavim aplikaciju otvorenu dok access token ne istekne - korisnik ne smije primijetiti ništa.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 3: route guardovi i permission-aware UI}
\begin{itemize}
  \item \codefile{router.beforeEach} guard: neprijavljeni korisnik ide na login
  \item Admin rute nedostupne običnom korisniku - direktan unos URL-a preusmjerava
  \item UI poštuje rolu: korisnik ne vidi admin akcije, admin vidi sve
  \item UI poštuje \textbf{poslovna pravila}: gumbi disabled kad pravilo zabranjuje akciju, npr. nakon isteka roka
\end{itemize}

\vspace{0.6em}
Guard je UX, ne sigurnost - backend i dalje mora zabraniti. Očekujte pitanje: \enquote{Što se dogodi ako korisnik ručno upiše admin URL? A ako pošalje request curlom?}
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 4: UX stanja}
Svaki view koji dohvaća podatke mora hendlati tri stanja:

\vspace{0.4em}
\begin{tabular}{@{}llp{5.5cm}@{}}
  \toprule
  \textbf{Stanje} & \textbf{Uvjet} & \textbf{Što korisnik vidi} \\
  \midrule
  Loading & čeka se API & spinner ili skeleton \\
  Error & request pao & poruka s retry gumbom \\
  Empty & nema podataka & jasna poruka i CTA za prvi unos \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
Prazna bijela stranica dok se čeka API, ili tablica bez retka i bez objašnjenja - to su stanja za koja skidam bodove. Retry nudite samo za mrežne i 5xx greške, ne za 4xx.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 5: forme i validacija}
\begin{itemize}
  \item \textbf{Klijentska validacija} prije slanja: obavezna polja, formati, rasponi
  \item \textbf{Serverske greške} prikazane na pravom mjestu:
  \begin{itemize}
    \item 422 - greška ispod odgovarajućeg polja, parsirana iz FastAPI \codefile{detail} formata
    \item 409 i 400 - globalna poruka iznad forme, npr. \enquote{Rok za prijave je istekao}
  \end{itemize}
  \item Submit gumb disabled dok request traje - nema duplih klikova
  \item Nakon uspjeha: redirect ili jasna potvrda, ne tiho ništa
\end{itemize}

\vspace{0.4em}
Pri pregledu namjerno šaljem nevažeće podatke i duplikat - forma mora reagirati smisleno na oba slučaja.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 6: state management}
\begin{itemize}
  \item \textbf{Pinia auth store}: user, token, \codefile{isAuthenticated}, \codefile{isAdmin}, login i logout akcije
  \item \textbf{Barem jedan store za poslovni entitet} s loading i error stateom
  \item Store za podatke koje dijeli više viewova; lokalni \codefile{ref()} za ono što živi u jednoj komponenti
  \item Pesimistički update: čekaj odgovor API-ja, pa ažuriraj state
\end{itemize}

\vspace{0.4em}
Pitanje koje sigurno dolazi: \enquote{Zašto je ovo u storeu, a ono lokalno?} Odgovor \enquote{tako je bilo u tutorialu} ne prolazi.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 7: TypeScript}
\begin{itemize}
  \item Cijeli frontend u TypeScriptu: \codefile{lang="ts"} u svim komponentama
  \item \textbf{Tipovi u \codefile{src/types/}} preslikavaju vaše Pydantic Response scheme 1:1
  \item Tipizirani API pozivi: \codefile{api.get<Lifter[]>(...)}, tipizirani propsi i emitovi
  \item \codefile{vue-tsc} prolazi \textbf{bez grešaka} - to je uvjet, ne preporuka
  \item \codefile{any} koristite samo gdje imate obrazloženje koje možete izgovoriti naglas
\end{itemize}

\vspace{0.4em}
TypeScript vam je saveznik protiv tipfelera u nazivima polja - greška se vidi u editoru, ne na obrani.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 8: testovi}
\begin{tabular}{@{}lp{6.8cm}@{}}
  \toprule
  \textbf{Tip} & \textbf{Minimum} \\
  \midrule
  Vitest unit & barem jedna utility funkcija i jedan store s mockanim API-jem \\
  Component test & barem jedna komponenta: renderiranje propsa i emitani event \\
  Playwright E2E & barem login flow: uspješna prijava i pogrešna lozinka \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
Testovi se pokreću s \codefile{npm run test} i moraju biti zeleni pri predaji. E2E test poslovne zabrane, npr. disabled gumb nakon roka, nosi dodatnu težinu na obrani.
\end{frame}

% ------------------------------
\begin{frame}{Zahtjev 9: deploy}
\begin{itemize}
  \item Aplikacija dostupna na \textbf{javnom URL-u}: Railway, Render ili slična platforma
  \item Backend i frontend deployani zasebno; baza je managed PostgreSQL
  \item \textbf{Env varijable}: \codefile{VITE\_API\_URL} za frontend; \codefile{DATABASE\_URL}, \codefile{JWT\_SECRET} i \codefile{CORS\_ORIGINS} za backend
  \item \textbf{CORS} ograničen na domenu vašeg frontenda, ne \codefile{*}
  \item \textbf{SPA fallback}: direktan URL bilo koje rute servira \codefile{index.html}
  \item Migracije se pokreću automatski pri deployu
\end{itemize}

\vspace{0.4em}
Deploy radimo zajedno na Predavanju 12 - ne ostavljajte ga za zadnji dan.
\end{frame}
