\begin{frame}{Modeli autorizacije: RBAC, ABAC, ACL}
\begin{tabular}{@{}lp{8cm}@{}}
  \toprule
  \textbf{Model} & \textbf{Kako radi} \\
  \midrule
  \textbf{ACL} (Access Control List) & Svaki resurs ima listu tko smije što (npr. Unix file permissions) \\
  \midrule
  \textbf{RBAC} (Role-Based) & Korisnik ima rolu, rola ima dozvole. Jednostavno za male sustave. \\
  \midrule
  \textbf{ABAC} (Attribute-Based) & Odluka na temelju atributa korisnika, resursa i konteksta. Fleksibilno ali složeno. \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
Naš projekt koristi \textbf{RBAC + ownership} - dovoljno za domenu, a studenti razumiju model.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Zašto RBAC za naš projekt?}
\begin{itemize}
  \item Imamo samo 2 role (\texttt{admin}, \texttt{club}) - RBAC je prirodan izbor
  \item ABAC bi bio overkill: nemamo složene politike poput \enquote{klub smije prijaviti samo liftera starijeg od 18 godina iz istog grada}
  \item ACL ne skalira: ne želimo definirati pristup za svaki resurs pojedinačno
\end{itemize}

\vspace{0.6em}
\begin{block}{Kad bi trebao ABAC?}
Kad imate 10+ rola, politike ovise o vremenu/lokaciji, ili pravilima koja se mijenjaju bez deploya.
\end{block}
\end{frame}

% ------------------------------------------------------------
\begin{frame}{OWASP Top 10: Broken Access Control (\#1)}
Od 2021., \textbf{Broken Access Control} je \#1 ranjivost prema OWASP-u. \\
OWASP je kratica za \textbf{Open Web Application Security Project} - neprofitna organizacija koja objavljuje liste najčešćih sigurnosnih propusta.

\vspace{0.6em}
Tipični propusti:
\begin{enumerate}
  \item Provjera pristupa samo na frontendu
  \item Endpoint bez ikakve provjere role
  \item Korisnik mijenja ID u URL-u i pristupa tuđim podacima
  \item API vraća podatke koje korisnik ne bi smio vidjeti
\end{enumerate}

\vspace{0.6em}
Naš projekt pokriva sve navedeno: backend provjerava rolu i ownership na \textbf{svakom} endpointu.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{IDOR: Insecure Direct Object Reference}
Napadač mijenja ID u requestu da pristupi tuđim podacima.

\vspace{0.6em}
\textbf{Primjer napada:}
\begin{enumerate}
  \item Korisnik kluba Behemot šalje: \texttt{GET /clubs/1/lifters} (svoj klub)
  \item Mijenja URL u: \texttt{GET /clubs/2/lifters} (klub Heraklo)
  \item Bez ownership provjere: vidi tuđe natjecatelje
\end{enumerate}

\vspace{0.6em}
\textbf{Obrana}: usporedba \texttt{current\_user.club\_id} s \texttt{club\_id} iz URL-a u service layeru.

\vspace{0.4em}
IDOR je najčešći oblik Broken Access Controla.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Principle of Least Privilege}
\begin{center}
\Large Korisnik smije \textbf{samo ono} što mu treba za posao. Ništa više.
\end{center}

\vspace{0.8em}
U praksi:
\begin{itemize}
  \item Club korisnik ne vidi API za kreiranje natjecanja - čak ni u Swagger dokumentaciji
  \item Admin ne modificira prijave klubova direktno - to je klubova odgovornost
  \item Endpointi koji vraćaju liste filtriraju prema roli: admin vidi sve, club vidi svoje
\end{itemize}
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Defense in Depth: višeslojni pristup}
Ne oslanjamo se na jednu provjeru:

\vspace{0.6em}
\begin{enumerate}
  \item \textbf{Transport}: HTTPS (enkriptirani promet)
  \item \textbf{Autentikacija}: JWT token verifikacija
  \item \textbf{Autorizacija - rola}: \texttt{require\_role} dependency
  \item \textbf{Autorizacija - ownership}: service layer provjera
  \item \textbf{Baza}: foreign key i unique constrainti
\end{enumerate}

\vspace{0.6em}
Ako jedan sloj zakaže, problem zaustavlja sljedeći.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{JWT claims: što stavljamo u token?}
Naš JWT payload sadrži:
\begin{itemize}
  \item \texttt{sub} - user ID
  \item \texttt{role} - \texttt{"admin"} ili \texttt{"club"}
  \item \texttt{club\_id} - ID kluba (null za admina)
  \item \texttt{exp} - istek tokena
\end{itemize}

\vspace{0.6em}
\textbf{Pravilo}: u token stavimo samo ono što nam treba za autorizaciju na \textbf{svakom} requestu.

\vspace{0.4em}
\begin{block}{Zašto ne čitamo rolu iz baze na svakom requestu?}
Performanse: upit u bazu na svaki request je skup. JWT je self-contained - sve što treba je u tokenu.
Trade-off: ako se rola promijeni, stari token i dalje ima staru rolu do isteka.
\end{block}
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Token revokacija: trade-off}
Problem: korisnik je deaktiviran, ali ima valjan token do isteka.

\vspace{0.6em}
Opcije:
\begin{enumerate}
  \item \textbf{Kratki tokeni} (15 min) - kompromis brzine i sigurnosti
  \item \textbf{Blacklist} - lista revociranih tokena (zahtijeva storage, npr. Redis)
  \item \textbf{Verzioniranje} - \texttt{token\_version} u bazi, odbijaj stare verzije
\end{enumerate}

\vspace{0.6em}
Naš projekt koristi kratke tokene (15 min access + refresh). Na obrani morate znati objasniti zašto nismo implementirali blacklist.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Auto-login: kreiranje kluba s korisnikom}
Kad admin kreira klub:
\begin{enumerate}
  \item Admin šalje: \texttt{POST /clubs} s \texttt{name}, \texttt{city}, \texttt{password}
  \item Backend kreira Club i automatski kreira User:
  \begin{itemize}
    \item \texttt{username = slugify(name)} - npr. \enquote{Behemot} $\rightarrow$ \texttt{behemot}
    \item \texttt{role = "club"}
    \item \texttt{club\_id = novi\_klub.id}
  \end{itemize}
  \item Response vraća klub podatke + generirani username
\end{enumerate}

\vspace{0.6em}
Club 1:1 User - svaki klub ima točno jednog korisnika za prijavu.

\vspace{0.4em}
Admin vidi username i prosljeđuje ga klubu. Klub se prijavi s username + password.
\end{frame}

\begin{itemize}

  \item \texttt{get\_current\_user} dependency izvlači korisnika iz tokena
  \item Danas: dodajemo sloj koji provjerava \textbf{smiješ li raditi to što tražiš}
\end{itemize}

\vspace{0.6em}
\begin{center}
\Large Autentikacija = tko si ti. \\ Autorizacija = smiješ li to.
\end{center}
\end{frame}

% ------------------------------------------------------------
\begin{frame}{Ownership: zašto rola nije dovoljna?}
\begin{itemize}
  \item Dva korisnika imaju rolu \texttt{club}
  \item Korisnik kluba \enquote{Behemot} ne smije uređivati natjecatelje kluba \enquote{Heraklo}
  \item Rola kaže \textbf{što smiješ raditi} - ownership kaže \textbf{nad čijim podacima}
\end{itemize}

\vspace{0.6em}
Ownership se provjerava usporedbom \texttt{current\_user.club\_id} s \texttt{club\_id} resursa.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{401 vs 403: kad koji?}
\begin{tabular}{@{}lp{8cm}@{}}
  \toprule
  \textbf{Status} & \textbf{Značenje} \\
  \midrule
  \textbf{401 Unauthorized} & Nisi se identificirao ili ti je token istekao. Ponovno se prijavi. \\
  \midrule
  \textbf{403 Forbidden} & Znam tko si, ali \textbf{nemaš pravo} na to. Ponovna prijava neće pomoći. \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
Česta greška: vratiti 401 kad bi trebao biti 403. To zbunjuje frontend koji pokušava refreshati token umjesto da prikaže \enquote{nemate pristup}.
\end{frame}

\begin{frame}[fragile,shrink=5]{Dependency: \texttt{require\_role}}
\begin{lstlisting}[language=python]
from app.core.errors import AppError

def require_role(*allowed_roles: str):
    def checker(
        current_user: User = Depends(get_current_user)
    ) -> User:
        if current_user.role not in allowed_roles:
            raise AppError(
                "forbidden",
                "Nemate dozvolu za ovu akciju",
                status_code=403,
            )
        return current_user
    return checker
\end{lstlisting}

\vspace{0.4em}
Factory pattern: \texttt{require\_role("admin")} vraća dependency koji propušta samo admine.
\end{frame}

\begin{tabular}{@{}lp{8cm}@{}}

\begin{frame}[fragile,shrink=5]{Alternativa: ownership kao dependency}
\begin{lstlisting}[language=python]
async def require_club_access(
    club_id: int,
    current_user: User = Depends(get_current_user),
) -> User:
    if current_user.role == "admin":
        return current_user
    if current_user.club_id != club_id:
        raise AppError("forbidden", "Pristup odbijen", 403)
    return current_user
\end{lstlisting}

\vspace{0.4em}
Ovo radi ako je \texttt{club\_id} uvijek u URL-u. Za složenije slučajeve ownership ostaje u serviceu.

\begin{frame}{Česte greške u autorizaciji}
\begin{enumerate}
  \item Provjera role samo na frontendu - backend je autoritet
  \item Ownership provjera samo po URL-u, ne po tijelu requesta
  \item Zaboraviti provjeriti ownership na UPDATE/DELETE
  \item Vratiti 404 umjesto 403 - otkriva postojanje resursa
  \item Ne testirati autorizaciju uopće
\end{enumerate}

\vspace{0.6em}
Na obrani testiram točno ovo: šaljem request s tokenom korisnika koji \textbf{ne bi smio} imati pristup.
\end{frame}

% ------------------------------------------------------------
\begin{frame}{404 vs 403: dilema otkrivanja resursa}
\begin{itemize}
  \item Ako vratim 403: napadač zna da resurs postoji
  \item Ako vratim 404: napadač ne zna, ali korisnik ne razumije zašto ne vidi podatke
\end{itemize}

\vspace{0.6em}
Uobičajena praksa:
\begin{itemize}
  \item Za javne resurse (natjecanja): 403 je ok, ionako su javni
  \item Za osjetljive resurse: 404 je sigurnija opcija
\end{itemize}

\vspace{0.4em}
U našem projektu koristimo 403 jer domena nije osjetljiva. Na obrani morate znati objasniti zašto.
\end{frame}

def test_club_user_cannot_create_club(client, club_token):
    r = client.post(
        "/clubs",
        json={"name": "Novi", "city": "Zagreb", "password": "pass123"},
        headers={"Authorization": f"Bearer {club_token}"},

def test_admin_can_create_club(client, admin_token):
    r = client.post(
        "/clubs",
        json={"name": "Novi", "city": "Zagreb", "password": "pass123"},
        headers={"Authorization": f"Bearer {admin_token}"},
    )
    assert r.status_code == 201
    assert r.json()["username"] == "novi"

\begin{frame}{Middleware vs dependency za autorizaciju}
\begin{tabular}{@{}lp{5cm}p{5cm}@{}}
  \toprule
  & \textbf{Middleware} & \textbf{Dependency} \\
  \midrule
  Kad se izvršava & Prije routera, na svaki request & Samo na endpointima koji ga koriste \\
  Granularnost & Gruba (po prefixu URL-a) & Fina (po endpointu) \\
  Pristup podacima & Samo request/response & Može primiti path parametre \\
  \bottomrule
\end{tabular}

\vspace{0.6em}
FastAPI dependency pristup je bolji za naš slučaj:
\begin{itemize}
  \item Različiti endpointi trebaju različite role
  \item \texttt{club\_id} iz URL-a nam treba za ownership provjeru
  \item Middleware ne može znati koji je \texttt{club\_id} relevantan
\end{itemize}
\end{frame}

\begin{frame}{Audit checklist: jeste li sve pokrili?}
Prije obrane provjerite svaki endpoint:
\begin{enumerate}
  \item Zahtijeva li autentikaciju? (\texttt{get\_current\_user} ili \texttt{require\_role})
  \item Provjerava li rolu? (admin-only vs club-allowed)
  \item Provjerava li ownership? (club smije samo svoje)
  \item Postoji li test za neautorizirani pristup?
  \item Je li response konzistentan? (401 vs 403 na pravom mjestu)
\end{enumerate}

\vspace{0.4em}
Ako imate 5 endpointa, trebate barem 5 testova za autorizaciju - po jedan negativni za svaki endpoint.
\end{frame}
